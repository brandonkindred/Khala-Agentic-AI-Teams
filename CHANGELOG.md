All notable changes to this repository are documented here.

## [Unreleased]

### Changed

- **Backend and frontend code-v2 teams merged into one `codegen_team` package.** `backend_code_v2_team` and `frontend_code_v2_team` — already unified at the phase-implementation level (see the entry below) but still two separate packages, each with its own `ToolAgentKind` enum, `orchestrator.py`, `models.py`, and `tool_agents/` tree — are now a single `software_engineering_team/codegen_team/` package, parametrized by a `stack: Literal["backend", "frontend"]` constructor argument on `CodegenTeamLead`/`CodegenDevelopmentAgent` (`codegen_team/orchestrator.py`) instead of two separate classes. `codegen_team/models.py` defines one unified `ToolAgentKind` (the union of both teams' members) and one `CodegenWorkflowResult`/`MicrotaskReviewConfig`; per-stack `StackProfile`/`V2TeamConfig` values, prompts, and the thin `problem_solving.py` wrapper live under `codegen_team/stacks/{backend,frontend}/`, and per-stack tool agents live under `codegen_team/tool_agents/{backend,frontend}/`. Backend's `run_code_review_fixes`/`run_qa_fixes`/`run_security_fixes`/`run_documentation_fixes` — previously the one piece of real per-team logic not yet folded into the shared phase layer — are now built by a shared `make_phase_fix_functions` factory in `shared/phases/problem_solving.py` and used by both stacks. Frontend's four remaining stub tool agents (`auth`, `api_openapi`, `state_management`, `linter`) are now real implementations: the first three are `FileGeneratorToolAgent` subclasses generating Angular/React auth guards, typed API client/service layers, and NgRx/Redux/signals store code respectively, mirroring backend's existing generators; `linter` runs `eslint --format json` via `run_frontend_lint_and_parse` and drives the same single-issue fix loop `build_specialist` uses. External behavior for existing callers is unchanged: `POST /backend-code-v2/run` and `POST /frontend-code-v2/run` (plus their status routes) keep their exact request/response shapes; a new `POST /code-v2/run` + `GET /code-v2/status/{job_id}` pair (`api/routes/code_v2.py`, `api/models.py`'s `CodegenRunRequest`/`CodegenRunResponse`/`CodegenStatusResponse`) takes an explicit `stack` field and dispatches through the same Temporal activities. `coding_engine_provider.py`'s `SECodeEngineProvider.build_implementation_team_lead` now resolves both `team_kind` values through one `_CODEGEN_TEAM_LEAD_MODULE` entry instead of a two-entry `_TEAM_LEAD_MODULES` registry; `temporal/activities.py`'s `_run_backend_code_v2_impl`/`_run_frontend_code_v2_impl` construct `CodegenTeamLead(get_client(stack), stack=stack)`. - **LLM failover — session-limit 429s now reset after 65 minutes, not 5 hours.** When a provider's 429 body classifies as a `session` usage-limit (e.g. Ollama Cloud's "session usage limit" phrase), `_mark_entry_exhausted` (`backend/agents/llm_service/factory.py`) computes `reset_at` as the error time plus `llm_config.failover_session_window_seconds()`, whose default (`backend/agents/llm_service/config.py`'s `_DEFAULT_FAILOVER_SESSION_WINDOW_S`) was `5 * 3600` — the provider stayed marked usage-limited and out of the failover rotation for 5 hours after every session-limit 429, far longer than most providers' actual session windows. The default is now `65 * 60` (65 minutes); the `LLM_FAILOVER_SESSION_WINDOW_S` env override is unchanged. Docs (`docs/ENV_VARS.md`, `llm_service/README.md`) and tests (`test_failover_config.py`, `test_failover.py`) updated to match.

The now-nonsensical `test_no_se_imports` AST guard (coding_team importing its own parent) is removed; coding_team's 34 test files moved into `software_engineering_team/tests/` (renamed `test_coding_team_*.py`, resolving the one real collision on `test_orchestrator_hitl.py`). ### Fixed

- **LLM service — a JSON-mode call with no explicit `think` and no per-agent pin now defaults to thinking off.** `resolve_think_for_model` (`backend/agents/llm_service/config.py`) resolved `think=None` to the model's platform-default (max) thinking tier regardless of `response_format`, so any `chat()`/`complete_json()` call that didn't explicitly pass `think=` ran full extended thinking even in JSON mode — extended thinking competes with strict JSON decoding for the content channel (the same failure mode `LLMSemanticExhaustionError.schema_forced` and the code-review thinking-downgrade retry exist to recover from), so a JSON-shaped call should default to thinking off rather than paying for a reasoning-only turn it then has to retry away. Symptom: `code_review_verify` (model `deepseek-v4-flash:cloud`, unregistered in `KNOWN_MODEL_THINKING_LEVELS` so it could only resolve to plain boolean `True`) logged `think=True rf=json` on every false-positive-verification call. `resolve_think_for_model` now takes a `response_format` keyword; when `think is None`, no per-agent `AGENT_DEFAULT_THINK` pin applies, and `response_format == "json"`, it resolves to `False` instead of falling through to the model's max tier. Deliberate per-agent pins (e.g. `code_review`'s reduced `"high"` tier) and any explicit caller-supplied `think` value are checked first and still win — this only changes the naked "no override at all" default. `OllamaLLMClient._resolve_think`/`_chat_impl`/`_complete_json_impl` and `ClaudeLLMClient.complete_json`/`chat` now thread `response_format` through to the resolver; `complete`/`complete_text` (never JSON-shaped) are unaffected and keep defaulting to the model's max tier. Tests: `llm_service/tests/{test_config,test_ollama_client,test_claude_client}.py` — existing default-resolution tests updated to assert the new JSON-mode-off default and moved to an explicit `think=True`/`think="max"` where their actual intent was exercising the thinking-downgrade ladder or the reasoning-effort wire mapping, not the default itself; new coverage for the JSON-vs-text-mode default split and the explicit-override-still-wins cases.

- **Investment / Temporal — the backtest activity now heartbeats and honors cancellation, mirroring paper-trading.** `run_backtest_activity` (`backend/agents/investment_team/temporal/workflows.py`) ran `_run_backtest_background` — a walk-forward sweep that can take up to 6 hours — directly, with no heartbeat, so Temporal had no way to detect a worker crash mid-run and no way to actually stop a cancelled run before it finished naturally. It now runs two background loops for the duration of the call: one calls `activity.heartbeat()` on a 30s interval (`shared.concurrency.BackgroundHeartbeat`, the same driver `run_paper_trading_activity` in the sibling `paper_trading.py` already uses) so Temporal can detect a worker crash; a second, much faster (0.25s) one polls the free in-memory `activity.is_cancelled()` and, only when `activity.cancellation_details().cancel_requested` is true (as opposed to a heartbeat timeout, worker shutdown, pause, or reset — which must leave the job alone so a Temporal retry can still resume the work instead of finding it pre-marked cancelled), cancels the job (`_bt_cancel_job`) so `_run_backtest_background`'s own existing cancellation checkpoints (already present, previously only reachable via the `/backtests/jobs/{job_id}/cancel` REST route) observe it and return `cancelled` instead of overwriting the job to completed/failed. `no_thread_cancel_exception=True` on the activity disables temporalio's default forced `CancelledError` injection into the activity's thread, which would otherwise race the poller and get caught by `_run_backtest_background`'s broad exception handler, misreporting the job as `failed`. A new `mark_backtest_job_cancelled_activity` compensation activity — mirroring `mark_paper_trading_stopped_activity` — cancels the job if the *workflow* itself is cancelled (e.g. directly via Temporal) while the activity is still merely scheduled and never gets a chance to run at all. `InvestmentBacktestWorkflow.run` sets a matching `heartbeat_timeout` (120s) on its `execute_activity` call so Temporal actually enforces the contract. Tests: `investment_team/tests/test_temporal_bootstrap.py` (heartbeat fires during a run, cancellation is observed via the fast poller decoupled from the heartbeat cadence, non-`cancel_requested` reasons leave the job alone, the compensation activity runs on workflow-level cancellation, the workflow passes `heartbeat_timeout`).
- **Deepthought — `test_events_emitted` no longer relies on a tautological `AgentEvent.model_fields` truthiness check.** `backend/agents/deepthought/tests/test_agent.py`'s event-emission test previously (per code-review findings #2922/#3087) asserted `AgentEvent.model_fields`, which is always truthy for any Pydantic model with fields and therefore validated nothing; that assertion was already gone from the test as of this change, superseded by checks that specific `AgentEventType` values appear in the emitted events. This adds the remaining hardening: a `{"event_type", "agent_id", "agent_name", "depth"} <= AgentEvent.model_fields.keys()` schema-contract check (fails if any of those fields is renamed/removed, unlike the old truthiness check) plus value-level assertions that each emitted event's `agent_id`/`agent_name`/`depth` actually match the executing agent.
- **Team service — auxiliary Postgres schemas registered from a team's `on_startup` hook no longer race the Temporal worker on cold start.** A prior fix registered a team's *primary* Postgres schema (`app.state.postgres_schema`, set by `create_team_app`) before the team-service wrapper starts that team's Temporal worker at import time — but a team could still register a *second*, auxiliary schema from its own FastAPI `on_startup` hook, which only runs once uvicorn's lifespan fires, after the worker had already started. `job_matching_team` was the one team doing this: it registered `user_profile.SCHEMA` from `_register_user_profile_schema` (called via `_on_startup`) while only `JOB_MATCHING_SCHEMA` was visible to the wrapper. On a fresh database this let a queued `job_matching_prepare_scan` activity read `user_profiles` before that table existed; the best-effort read in `career_store.load_career_profile` swallowed the "undefined table" error, logged a WARNING, and silently fell back to the bundled YAML example profile instead of the real one. `create_team_app` (`shared.app/factory.py`) now accepts `extra_postgres_schemas` and exposes the full ordered set — primary first, then extras — as `app.state.postgres_schemas` (each schema registers independently best-effort, so one schema's DDL failure never blocks another's, nor `on_startup`); `app.state.postgres_schema` is unchanged for backward compatibility. The team-service wrapper (`team_service/entrypoint.py`, `build_wrapper_body`) now reads `app.state.postgres_schemas` and registers every schema in a loop — each in its own try/except — before starting the Temporal worker, reusing the existing `TEMPORAL_ADDRESS`-gated block. `job_matching_team` (`job_matching_team/api/main.py`) now declares `USER_PROFILE_SCHEMA` via `extra_postgres_schemas` instead of registering it from `on_startup`; `_register_user_profile_schema`/`_on_startup` are removed, with `on_startup` now passed `_start_temporal_worker_backstop` directly. Teams with a single schema, and local/dev/test runs with `TEMPORAL_ADDRESS`/`POSTGRES_HOST` unset, are unaffected. Tests: `shared.app/tests/test_factory.py` (multi-schema exposure, ordered registration, one-schema-failure isolation), `team_service/tests/test_entrypoint.py` (updated ordering assertions plus a new test that executes the generated Temporal block against fakes to prove real multi-schema iteration and continue-past-failure), `job_matching_team/tests/test_api.py`, and new `job_matching_team/tests/test_schema_registration.py` (a live-Postgres regression test — with a negative control — proving the race is closed against a database where `user_profiles` was freshly dropped).
- **Code review — the reviewer no longer posts `[HIGH] … This code could not be reviewed automatically (…)` comments on PRs, and makes that failure rare.** When a chunk's review failed with a model-content error that survived recovery (most often `LLMSemanticExhaustionError` — a thinking model that returned reasoning but no final JSON — or `LLMTruncatedError`), the coordinator emitted one blocking `high` "not reviewed" finding per segment, which was published as an inline PR comment and rejected the whole review. That is a reviewer-side hiccup, not a code defect, yet it blocked PRs and read like a real finding. Three changes: (1) **Graceful degradation** — such a chunk now degrades non-blockingly by default: the range is recorded on the new `CodeReviewOutput.not_reviewed_ranges` (observability) and in a telemetry log, but is never posted and never blocks; the chunks that did review drive the verdict. The total-failure guard still raises `CodeReviewUnavailableError` when *no* chunk could be reviewed, and the new `CODE_REVIEW_BLOCK_ON_UNREVIEWED` opt-out restores the legacy fail-closed blocking behavior. (2) **Root-cause reduction** — before degrading, a last-resort retry re-runs the chunk with thinking forced off (`CODE_REVIEW_THINKING_OFF_RETRY`, default on) plus a prompt-level "emit only the JSON" nudge, turning the reasoning-only case into a real review. (3) **No raw errors on PRs** — the `/review-pr` flow's reviewer-failure and no-output paths now record the failure in the job store but post at most a single neutral, non-blocking note (`PR_REVIEW_POST_OUTAGE_NOTICE`, default on) instead of `Coding team job X failed: <raw exception>`; the "no engine provider configured" deploy-misconfig abort is unchanged. Files: `backend/agents/software_engineering_team/code_review_agent/{models,mapping,coordinator,chunk_reviewer,model_resolution}.py`, `backend/agents/coding_team/api/{orchestration,pr_review,main}.py`. Env: `CODE_REVIEW_BLOCK_ON_UNREVIEWED`, `CODE_REVIEW_THINKING_OFF_RETRY`, `PR_REVIEW_POST_OUTAGE_NOTICE`. Tests: `backend/agents/software_engineering_team/tests/{test_code_review_coordinator,test_code_review_e2e,test_code_review_cache,test_chunk_reviewer}.py`, `backend/agents/coding_team/tests/test_review_pr.py`.
- **Investment / Strategy Lab — stop-loss / take-profit alignment checks no longer treat a trigger as a hard price bound.** The deterministic trade-alignment gate's stop-loss check (`DeterministicAlignmentChecker._check_stop_loss` in `backend/agents/investment_team/strategy_lab/quality_gates/alignment_checks.py`) flagged any trade whose `return_pct` fell below the spec's stop floor (with only a 0.5pp slack) **and** was not attributed to `engine_exit:stop_loss` as a **critical** misalignment, which set `aligned=False` and made the analysis agent publish prose like *"the hard 10% stop-loss was not enforced: trade #3 realized a -13.94% loss … directly breaching the intended risk limit."* That is a category error: a stop-loss is a **trigger** that submits a sell order, not a cap on realized loss — prices gap between bars and carry a bid/ask spread, so the fill (and therefore realized loss) routinely lands past the threshold, and a non-attributed close past the floor simply means the strategy or another exit rule closed the position (the stop's purpose — exiting to limit further loss — was still served). The check now emits an **informational, passing** row instead of a critical one; the symmetric take-profit ceiling check (`_check_take_profit`) is corrected the same way (a gap-up fill past the ceiling, or an earlier exit, is expected, not a misalignment). This removes the redundant, false-positive per-trade floor/ceiling criticals; genuine "stop never fired" enforcement leaks remain owned by `ExitRuleConformanceGate`, which already excludes strategy-closed gap-down trades and uses per-symbol firing telemetry the per-trade view lacks. Engine-attributed (`engine_exit:stop_loss` / `engine_exit:take_profit`) and trailing-basis paths are unchanged. Tests: `tests/test_alignment_checks.py` (stop-loss / take-profit past-threshold cases rewritten to assert informational-pass + `aligned=True`, with a guard against "breach" framing in the finding details).
- **Investment / Strategy Lab — per-trade loss and position size are one quantity; `max_loss_per_trade_pct` removed.** The deployed position size *is* the most a single trade can lose (an entered position can lose up to ~100% of what it deploys), so the per-trade loss cap and the position-size cap were duplicate values expected to be equal. They are now consolidated onto `max_position_pct` (the clearer name) and `max_loss_per_trade_pct` is removed from `RiskLimits` (`backend/agents/investment_team/execution/risk_filter.py`); `from_legacy_dict` drops the retired key and the authored `max_position_pct` stands — the two are NOT folded together, because under the old model `max_loss_per_trade_pct` was a different quantity (a stop-governed realised-loss tolerance, `fraction × stop`), so importing it as a deployed-capital cap would wrongly shrink the position (e.g. `{max_position_pct: 10, max_loss_per_trade_pct: 0.5}` from a 10%-deployed × 5%-stop spec would collapse to a 0.5% cap, a 20× reduction), and a legacy `0`/negative/`None` value would silently zero or fail to validate the cap. This retires the readiness gate's Rule 9 "Check B" — the `risk_limits:loss_tolerance`, `risk_limits:loss_tolerance_no_stop`, `risk_limits:zero_loss_tolerance`, and `risk_limits:custom_code_unenforceable` criticals — leaving the deployed-cap check (`sizing:position_cap`) plus the prose-deployment warning; and removes the redundant runtime `_cap_qty_to_loss` clamp (the position clamp already enforces `max_position_pct`). `stop_loss.pct` is now correctly modeled as an independent, optional within-position safeguard — a price move off entry, never multiplied into the cap. A SHORT can lose more than 100% of deployed capital (price can more than double), so `TradingService` now auto-injects a 100%-adverse-move stop (`StopLossRule(pct=1.0, basis="entry_price")`) for any short that lacks an effective stop, bounding a short's modeled worst-case loss at the deployed size too. Design prompts (`design_system`, `design_review_system`, `design_self_review_system`) were corrected to teach the deployed-cap model. Tests: `tests/{test_spec_readiness,test_engine_entry_dispatch,test_trading_service,test_engine_exit_enforcement,test_orchestrator_helpers,test_audit_recent_runs}.py`.
- **Investment / Strategy Lab — crypto `-USD` canonicalization hardened against compound and empty suffixes.** `canonical_symbol(symbol, asset_class)` (`backend/agents/investment_team/symbols.py`) stripped only a *single* trailing `-USD` via an `if`, with no guard against an all-suffix input. A compound-suffixed crypto ticker (`DOGE-USD-USD`) therefore collapsed to `DOGE-USD`, missed the `YAHOO_CRYPTO_TICKERS` lookup, and was re-suffixed by the Yahoo fallback back into the malformed `DOGE-USD-USD` — the exact double-suffix the centralized normalization was meant to eliminate, just one cycle later; a literal `-USD` collapsed to an empty alias that was rebuilt into `-USD` and sent verbatim to yfinance. The helper now strips *every* trailing `-USD` with a `while` loop (`DOGE-USD-USD → DOGE`) and raises `ValueError` when a crypto symbol collapses to empty (`-USD`, `-USD-USD`), treating it as the invalid input it is rather than forwarding a malformed bare ticker to a provider or the cache. Because every provider path and the content-hashed market-data cache route through this single helper, the fix covers Yahoo, Twelve Data, Alpha Vantage, and CoinGecko at once. Tests: `tests/test_market_data_service.py` (compound-suffix + empty-raise unit cases, plus Yahoo and CoinGecko provider-level regressions).
- **Investment / Strategy Lab — indicator functions accept `list[Bar]` / `list[float]`, not only `pd.Series`.** Strategy sandbox runs were consistently failing with `'list' object has no attribute 'ewm'` (mis-reported as `error_type=lookahead_violation`) because the code-synthesis prompt documents `ctx.history(symbol, n) -> list[Bar]` while the shared indicator helpers silently required `pd.Series`. When generated strategy code passed the history list straight into `ema(history, period)`, the `.ewm`/`.rolling` call blew up on a plain `list`. The fix coerces at the single boundary we control: a new `_coerce_series(series, field="close")` helper in `strategy_lab/executor/indicators.py` accepts `pd.Series` (pass-through), `list[float]`, `list[Bar]`/OHLCV objects (extracts the field), and `list[dict]`, and every public indicator (`sma`, `ema`, `rsi`, `macd`, `bollinger_bands`, plus the multi-series `atr`, `adx`, `stochastic`, `vwap` with per-argument field extraction) now coerces its inputs up front. Bad input raises a clear `TypeError` (never `AttributeError`). The streaming harness (`trading_service/strategy/streaming_harness.py`) no longer mislabels an indicator-module `AttributeError` as `lookahead_violation` — it classifies traceback frames originating in `indicators.py` as `runtime_error`. The synthesis prompt now documents that indicators accept the `list[Bar]` from `ctx.history` directly. The coercion also accepts an object-dtype `pd.Series` (preserving its index), generic non-string sequences (`collections.deque`, `np.ndarray`), and validates every element (rejecting `bool` anywhere and normalising malformed-element failures to `TypeError`). Separately, the indicator return-type contract is now consistent across both execution paths: a new scalar-returning `strategy_lab/executor/strategy_indicators.py` (latest value per indicator; tuples for `macd`/`bollinger_bands`/`stochastic`) is the single source of truth shared by the streaming sandbox (copied in as `indicators.py`, with the Series implementation alongside as `_indicators_impl.py`) and the predicate-conformance shadow gate — previously the sandbox exposed the Series-returning module while the gate returned scalars, so a strategy using `if ema(history, 20) > bar.close` worked in one path and raised pandas' ambiguous-truth error in the other. The Series-returning `executor/indicators.py` remains the engine-internal implementation (predicate evaluator, rule probes). ### Fixed

- **Coding team UI: "Confirm & Start" on a GitHub issue no longer fails with an opaque `0 Unknown Error`.** The unified API image now installs `git` (the GitHub issue-to-PR route shells out to it to clone/fetch the target repo), the shared team-service image installs `git` for the coding team's branch/commit/push during code-generation jobs, and `POST /api/integrations/github/run-issue` now converts clone/timeout/connection failures into explicit `502`/`503`/`504` responses instead of unhandled `500`s — those were emitted outside the CORS middleware, so the browser dropped the response and the UI could only surface a status-0 error. `_ensure_repo_clone` no longer lets `subprocess` errors escape and scrubs the token from `git fetch` stderr. The coding-team service now also threads the GitHub credential through its own network git operations (`_prepare_issue_branch` fetch and `_push_branch` push) using the same transient `GIT_CONFIG_*` Bearer-header pattern as the clone — the token is never persisted to `.git/config`, which matters because the checkout lives on the shared `agents_data` volume; without it a default checkout had no credentials and the background job would fail at push (or hang until the git timeout) after `/run-issue` already returned success. Code: `backend/Dockerfile`, `backend/team_service/Dockerfile`, `backend/unified_api/routes/integrations.py`, `backend/agents/coding_team/api/main.py`. Tests: `backend/unified_api/tests/test_integrations_github_route.py` (19 cases), `backend/agents/coding_team/tests/test_github_source.py` (credential-threading cases).
- **Investment / Strategy Lab — non-finite-OHLC defense now applied across every market-data provider, and Rule 5 no longer drops the price defense for fractional asset classes.** Two related data-integrity gaps where a safeguard existed on one path but not its siblings. (1) The non-finite-OHLC row filter lived only in the yfinance helper (`_df_to_bars`); the Twelve Data and Alpha Vantage ingest loops built bars with `round(float(...))` and no finiteness check, so when Yahoo cascaded to a fallback whose response carried a NaN (or a string `"nan"`), the row became an `OHLCVBar` with NaN fields and tripped the downstream sizing-realisability gate with "got nan" — intermittently, depending on which fallback the chain landed on. The round/finite-check/H-L-envelope-repair logic is now centralized in a shared `MarketDataService._normalize_ohlc_bar(...)` helper used by all four provider paths (yfinance, Twelve Data, Alpha Vantage, and CoinGecko, whose aggregated price list could likewise surface a NaN through `max()/min()`); each path drops non-finite rows identically and logs the dropped count. (2) `SpecReadinessGate._check_sizing_realisability` short-circuited the per-symbol price loop for fractional classes (forex/crypto), discarding the only NaN/zero/negative-price defense; a persistently broken provider (a `0.0` parsed from a rate-limit body, a negative sentinel, or persistent NaN) was silently ignored. The loop now runs for every asset class: a finite non-positive price is a broken-provider critical regardless of class; a non-finite price stays a hard critical for whole-lot classes but, for fractional classes, is tolerated when any symbol still resolves to a finite price (transient weekend/holiday gap) and downgraded to a non-blocking warning only when it affects every symbol. Code: `backend/agents/investment_team/market_data_service.py`, `backend/agents/investment_team/strategy_lab/quality_gates/spec_readiness.py`. Tests: `tests/test_market_data_service.py`, `tests/test_spec_readiness.py`. (Provider `float(None)`/`float(pd.NA)` TypeError-safety is tracked separately and intentionally out of scope.)
- **Investment / Strategy Lab — crypto `-USD` symbol normalization centralized across all market-data providers and the cache.** Previously only the Yahoo and CoinGecko fetch paths stripped a trailing `-USD` from crypto tickers, so a spec using `target_symbols=['BTC-USD']` that fell through to the Twelve Data or Alpha Vantage fallback produced a malformed `BTC-USD/USD` (Twelve Data) or a not-found bare `BTC-USD` (Alpha Vantage), surfacing as a generic "symbol unavailable" instead of correct data. Normalization now happens once in a shared `canonical_symbol(symbol, asset_class)` helper (`backend/agents/investment_team/symbols.py`): `MarketDataService._fetch_with_providers` collapses crypto tickers to their bare alias before the provider chain, so all four providers receive the same canonical input and re-suffix it to their own convention. The same helper runs at the `fetch_ohlcv_range` / `fetch_multi_symbol_range` entry points to key the content-hashed market-data cache, so the bare alias and the Yahoo-suffixed form of a coin (`BTC` / `BTC-USD`) now share a single snapshot and fingerprint instead of being cached as two distinct datasets; the result dict and `provider_used` are re-keyed back to each caller's original symbol so downstream provenance and target-coverage logic are unaffected. Code: `backend/agents/investment_team/{symbols,market_data_service}.py`. Tests: `tests/test_market_data_service.py`, `tests/test_market_data_extras2.py`.
- **`user_agent_founder` spec generation:** the "Startup Founder Testing Persona" run no longer fails with `LLMJsonParseError` when the model returns Markdown. `FounderAgent.generate_spec` now bypasses the Strands / `chat_json_round` JSON-only transport and calls `LLMClient.complete` directly via a new `_call_text` helper. `FounderAgent.answer_question` migrated to `generate_structured` with a `FounderAnswer` Pydantic schema (canary for the new API); the bespoke regex/`json.loads` fallback was removed in favor of the self-correction guard.
- **Ollama structured JSON:** responses with unescaped double quotes inside string values (common when the model cites snippets like `"Resource": "*"`) are parsed using a **`json-repair`** fallback in `OllamaLLMClient._extract_json`. Blog copy-editor prompt updated to require escaped or single-quoted inner quotes.
